# Search and A* — Lab Answers

## Task 0 — Formal Search Problem

The warehouse navigation problem can be described using the following components:

| Search element    | Description                                       |
| ----------------- | ------------------------------------------------- |
| State             | Robot location represented by `(row, column)`     |
| Available actions | Up, Down, Left, Right                             |
| State transition  | Move into a neighbouring cell that is not blocked |
| Starting state    | Cell marked `S`                                   |
| Target state      | Cell marked `G`                                   |
| Movement cost     | `1` for every move                                |

### (a) State representation

The robot only needs its current grid coordinates to identify its state. Therefore, a state can be represented as:

```text
(row, column)
```

### (b) Invalid actions

A movement cannot be performed if the resulting position is outside the warehouse boundaries or corresponds to an obstacle.

### (c) Determinism

The environment is deterministic. Once the current state and movement direction are known, the resulting state is fixed.

### (d) Solution

A solution consists of an ordered list of legal movements that takes the robot from `S` to `G`.

# Task 4 — Understanding the A* Implementation

The main elements of the implementation correspond to the standard A* formulation:

| A* component         | Implementation                   |
| -------------------- | -------------------------------- |
| State                | `(row, column)`                  |
| Actions              | Generation of neighbouring cells |
| Transition           | Legal adjacent position          |
| Goal test            | `current == goal`                |
| Cost-so-far `g(n)`   | `g_cost` dictionary              |
| Heuristic `h(n)`     | Selected heuristic function      |
| Evaluation `f(n)`    | `g(n) + h(n)`                    |
| Frontier             | Python `heapq` priority queue    |
| Search information   | `g_cost` and parent mappings     |
| Route reconstruction | `reconstruct()`                  |

### Questions

**(a) How is the A* frontier represented?**

A priority queue is used to store the states waiting to be expanded.

**(b) Which state is selected next?**

The state with the smallest current `f(n)` value has the highest priority and is selected for expansion.

**(c) Where does the heuristic come from?**

The heuristic value is generated by the selected heuristic function. For the standard experiment this is the `manhattan()` function, while the alternative experiments use their corresponding heuristic definitions.

**(d) Does the implementation explicitly calculate `f(n)`?**

Yes. When a successor is considered, its priority is calculated from the newly obtained path cost and the heuristic estimate:

```text
f(n) = g(n) + h(n)
```

**(e) What is the purpose of `g_cost`?**

The dictionary keeps track of the cheapest known route to each state. A state does not need to be inserted again when the newly discovered route is not cheaper than the one already recorded.

# Task 5 — BFS and A* Results

Both search methods successfully reached the destination on the supplied warehouse.

For the tested implementation, the observed path lengths were:

```text
BFS             40 moves
A* (Manhattan)  40 moves
```

The number of expanded states is not necessarily identical across implementations because details such as priority-queue ordering and tie-breaking can affect which states are explored first.

The important distinction is that A* incorporates information about the destination through `h(n)`, whereas BFS does not use such goal-directed information.

# Task 6 — Changing the Heuristic

The experiment considers several choices for the heuristic.

### Case 1 — `h(n) = 0`

With the heuristic removed, the evaluation becomes dependent only on the accumulated path cost.

This makes the search equivalent to uniform-cost search. Since every warehouse movement has cost `1`, its behaviour is closely related to BFS.

### Case 2 — Euclidean Distance

Euclidean distance measures the straight-line distance between the current state and the goal.

It provides a lower-bound estimate for the number of horizontal and vertical movements required. However, Manhattan distance corresponds more directly to the movement restrictions of this particular grid.

### Case 3 — `2 × Manhattan Distance`

Doubling the Manhattan estimate makes the heuristic more aggressive.

The usual admissibility condition is:

```text
h(n) ≤ h*(n)
```

where `h*(n)` is the actual minimum remaining cost.

Multiplying Manhattan distance by two can make the heuristic larger than the true remaining cost. Consequently, the usual guarantee that A* returns an optimal path no longer necessarily applies.

The implementation records the following for each heuristic:

* Whether the goal was reached.
* Length of the resulting route.
* Number of states expanded.

# Task 7 — Reflection on Testing

The implementation was checked using several different environments instead of relying only on the main warehouse example.

The most useful cases were:

* The original warehouse.
* A simple one-move example.
* A warehouse where the destination cannot be reached.

These cases cover successful navigation, a minimal successful search, and failure handling.

The impossible configuration is especially useful because it checks whether the search terminates correctly when there is no route to the goal.

In addition to checking whether a path was returned, the resulting route was examined to ensure that consecutive positions correspond to legal single-cell movements. Path length was also checked as part of the validation.

# LLM Development Reflection

The LLM was used to help translate the search requirements into Python structures and implement the A* procedure.

However, generated code was treated as an initial solution rather than as evidence that the algorithm was correct.

Running independent tests was important because code can produce a seemingly reasonable route while still containing an error in the search logic, heuristic calculation, or termination condition.

The testing process therefore focused on both **whether a solution was produced** and **whether the produced solution actually satisfied the requirements of the search problem**.
